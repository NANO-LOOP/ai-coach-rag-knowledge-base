# 场景与数据生成约定

版本：0.2.0；状态：专家可维护的输入设计草案。场景 Skill 读取本页执行。字段、阶段能力与缺省统一以 [输入模型](input-model.md) 为准；未指定阶段时使用 T0。目标是生成具有不同判断分支、可供专家讨论和复验的场景，不预设唯一正确诊断。

## 从专家意图开始

| 进入方式 | 处理方式 |
| --- | --- |
| 专家给一句话或一段经历 | 提取已经给出的条件，仅追问影响场景方向的关键缺口，直接形成场景 |
| 专家只给运动或主题 | 提供 2–3 个不同问题方向供选，或用一个关键问题缩小范围 |
| 专家不知道怎么描述，希望被引导 | 按下方引导顺序逐步问，已有答案不重复问 |
| 专家说“你来选／直接生成” | 从已读知识与覆盖缺口选题，说明构造假设，不要求额外填表 |
| 专家要求多个场景或反例 | 先确定要覆盖的差异，再生成对照组或多样化场景组 |

没有主题时，可以问：“你想先看哪种运动，以及运动前准备还是运动后复盘？也可以让我推荐。”提供跑步、羽毛球、骑行等方向帮助选择，但不限于这些项目。HYROX 是可选示例，不是新场景的唯一来源。专家要求直接开始时，不因信息不足停在问卷里。

## 少量关键描述即可生成

重点获得三个信息：**什么运动与情境、想观察什么问题、目前知道什么**。经验、训练目标或限制仅在会改变场景时再补充；专家无需懂 JSON、分层、阶段或算法。

可自然询问：

1. “想模拟哪种运动，运动前还是结束后？”
2. “最想让 Coach 处理什么困惑，或者观察哪种表现？”
3. “已经有些什么信息？例如一段主观感受、训练记录、问卷或状态数据。”

一次只问当前最有价值的问题；通常 1–3 个关键问题足够，不机械走完。专家原话已包含答案时跳过；这是场景设计访谈，不消耗运动者 Coach 的提问预算。背景不完整时可提出少量明确标注的构造设定；未知的原因、未回答的个人事实、算法资格及安全检查不能为凑完整而默认成立。

例如专家说“一个业余羽毛球爱好者，今天总感觉慢半拍，想看 Coach 怎么问”，可以只追问这是运动前担心还是运动后感受；若上下文已明确结束，则直接整理可见事实，不再问。睡眠、训练负荷和注意状态保留未知，不能自行认定某个原因。

## 多样性来自判断差异

从下表选择与任务有关的维度，不做所有组合，不给每个场景堆满变量。

| 维度 | 可变化内容 |
| --- | --- |
| 运动与情境 | 耐力、间歇、技术或精度项目；训练/比赛；运动前/后 |
| 运动者目标 | 完成训练、理解表现变化、调整准备、检验先前建议；经验与现实限制 |
| 问题类型 | 疲劳感、精力或压力变化、发挥波动、主观与记录不一致、表现正常无需调整 |
| 输入条件 | 信息充分、关键项缺失、只有自报、部分算法有效、来源冲突、时间不明确 |
| 个人历史 | 首次使用、有近期记录、记录不足以比较、具备合格个人比较依据；受阶段限制 |
| 回答分支 | 支持、否定、记不清、拒答、纠正、前后矛盾；后续回答不放进初始输入 |
| 建议后续 | 尚无反馈、部分执行、执行但不可比、可比但无改善；仅在阶段允许时使用 |
| 知识覆盖 | 有相关草稿、知识不完整、需要专家补充适用条件；不得把草稿包装成已验证结论 |

先读 [专题目录](../knowledge/topics/README.md) 和 [覆盖情况](../knowledge/coverage.md) 定位，再实际读取用到的知识正文。没有完整问题包也可以构造讨论案例；缺少专项依据时标为探索性场景，列出知识缺口，不从其他运动直接搬用专项机制、剂量或阈值。

生成一组多样化场景时，每例应具有不同的主要未知或决策难点；记录与已有场景的实质差别。若只换项目名、人名或数值而判断分支不变，应合并或重做。复杂场景可以组合多个因素，但必须标出核心问题，避免信息堆砌。

## 两种场景组

- **覆盖组**：用于发现知识和 Agent 能力缺口。先给简短场景列表，标明项目、问题、输入条件及要观察的行为；按专家指定数量生成，未指定时先提供三个不同方向，选定后再展开。明确要求全部展开时直接完成。
- **对照组**：用于验证一条判断规则。复制同一基线，尽量只改变一个关键事实或证据条件，保留父场景、变更字段和版本。至少考虑一个可能支持和一个可能推翻假设的版本，需要时增加未知或冲突版本。未来回答放在独立角色材料中，不能提前提供给 Coach。

专家指定具体数量、运动、阶段、难度或排除项时优先遵守；不得为满足多样性擅自增加阶段不支持的数据。

## 生成与交付

1. 用一句话概括场景问题，区分专家给定事实、构造设定、未知和仅用于观察的候选假设。需要整理时用 [场景设计单](templates/scenario-brief.md)，由 Agent 填写，不要求专家填表。
2. 从 `agent/contracts/defaults/<阶段>.json` 复制 `initial_input.json`，按 Schema 填写允许字段，mode=synthetic。所有构造数据保留 synthetic 来源和模拟来源类型；数值具有单位和时间，未知保留带原因的 null。不为了“看起来真实”补造有效算法输出、比较资格或通过的安全检查。
3. 同步生成 `scenario.md` 阅读摘要及 `simulation_meta.json`。元数据记录场景身份/版本、阶段、构造假设、变更字段、实际读取的输入规则与知识版本/哈希。设计目的、预期行为、知识缺口只留专家侧；JSON 是可见事实源，摘要不另存一套事实。
4. 专家默认扮演运动者。起始可见信息与后续答案分开；需要预设角色信息时放入 `athlete-role.md`。没有指定后续经历时，不为专家预编答案。场景描述中也不能用标题或摘要泄露隐藏原因。
5. 执行 `node agent/contracts/scripts/check-input.cjs <输入文件>`，然后按下方标准走读语义；校验依赖不可用时如实记录。结构通过不代表生理合理或建议有效。
6. 向专家呈现：**场景、已知信息、关键未知、可调整设定**。准备完成后交 Coach 模拟；不输出预定正确诊断或全套未来问答。收到新的场景设定时增加版本，保留原始快照。

## 生成质量检查

- **符合描述**：保留专家锁定条件；新增构造设定可识别，不伪称专家提供。
- **阶段一致**：T0 不生成执行效果和个人区间比较数据；其他阶段以当前配置为准。
- **语义一致**：身份、时间、运动前后、数据来源和单位相容；事后行为不能解释此前表现。刻意设置的来源冲突保留为冲突，不能假装已经消解。
- **有讨论价值**：关键未知可能改变分析或行动；也允许“信息充分、不必追问”和“依据不足、不能建议”的场景。
- **真正有差别**：覆盖组的主要问题不同；对照组清楚标出改变了什么及为何值得比较。
- **不泄露答案**：起始输入、标题和 Coach 可见摘要只包含已知事实；测试预期在专家侧。
- **专业边界明确**：数值、机制、建议的依据可追溯，未核验项保持待审；缺少知识不能通过生成案例假装补齐。

如果同一会话已读到角色隐藏信息，后续只能称为带上下文的演示。独立验证需要实际只接收可见输入的模型环境，不能凭“忽略上文”声称隔离。生成后的结构校验、人工走读、专家审阅和实际 Coach 行为验证分别记录。

批量生成与引导过程的验收见 [验证设计](evaluation.md)。当前文档定义生成方法，不代表已经证明所有运动场景的生成质量。
