# 专家维护范围与 Skill 边界

本工作台采用四个功能 Skill 和一个协调入口。场景设计与结构化数据生成属于同一个功能。Skill 负责定位文档、调用流程、角色分流和记录交接；专业规则与 Coach 决策规则在对应文档维护，不在 Skill 内复制第二份。

## 三类可维护资产

| 专家意见 | 主入口 | 配套修改与检查 |
| --- | --- | --- |
| 输入缺字段、数据含义或阶段缺省不合理 | [输入模型](../agent/input-model.md) | 同步 contracts 中的 Schema、profiles、defaults、examples 和必要测试；场景生成方式见 [生成约定](../agent/scenario-generation.md) |
| 提问顺序、判断、建议或知识使用方式不合理 | [Coach Agent 架构](../agent/README.md) | 同步回合契约、对话原则、记录模板及验证场景 |
| 专业内容、依据、条件或目录组织不合理 | [知识结构](../knowledge/STRUCTURE.md) 和对应 knowledge/ 正文 | 同步版本、引用、审阅记录与目录索引 |

只修改某个案例的事实，落到该场景版本，不自动改输入模型；一次用户回答或某位专家的偏好，不自动升级成通用规则。一次意见可以涉及多个资产，分别说明修改理由。

专家可以用自然语言提出意见，由访谈 Skill 澄清，由整理 Skill 修改。明确要求修改时可直接完成相应草稿，不为普通文档修订反复确认。共享修改保留来源、版本、差异和未解决问题；专业审阅、规则认可、结构校验与模型验证分别记录。

## Skill 的特殊修改流程

以下属于稳定的执行层：skills/ 下的 SKILL.md、references、配置与调用元数据，以及承载同类规则的仓库协议和本页维护边界。不能通过把相同规则搬进可编辑文档来绕过此边界。

先判断能否在三类资产中解决。只有涉及调用路由、模式切换、工具权限、记录交接或 Skill 执行方式，才提出 Skill 修改；不能把“Coach 问得不对”直接解释为改 Skill。

1. **确认修改意图**：说明涉及哪项执行规则、为什么修改底层文档不足以解决，确认专家确实要修改 Skill。明确提出改 Skill 的原话可以作为这一阶段的确认；含糊反馈不能代替。
2. **确认具体差异**：先在 review-data/<session-id>/skill-change-proposal.md 形成方案，列出目标文件、原版本/哈希、具体差异、影响与验证方式。展示后再取得对该差异的明确确认，才写入执行层。只同意整理意见不算同意改 Skill；差异发生实质变化时重新确认。
3. 写入后检查技能格式、引用、清单哈希及相关行为，记录实际结果。授权 Git 提交不等于认可专业内容或授权额外工具。

这是遵循用户要求的会话操作约定，不是文件系统权限隔离。提出 Skill 修改期间，其他已授权且不依赖该修改的文档工作继续完成。

## 文档如何影响下一次模拟

场景生成先读输入模型；Coach 模拟先读 Agent 架构及其回合契约。两者按需要读取相关知识正文，记录实际使用的版本/哈希。Skill 保存读取与执行方式，不保存另一套字段、阶段能力或决策规则。

输入文档与 Schema 不一致时先报告差异并同步修订，不静默挑一份执行，也不虚报校验通过。文档中的领域规则不能覆盖角色识别、写入确认和工具权限。

修改后重读相关文件，用同一输入重跑受影响部分；保留此前输出和所用版本。输入模型发生变化时创建新输入版本，不覆盖历史快照。专家讨论结束后，收到“继续模拟”再恢复。没有实际运行则记录未运行。
