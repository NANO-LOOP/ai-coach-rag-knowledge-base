# 知识库维护与研发交付
位置与执行方式见 [飞书维护](references/feishu.md)，知识单元及交付约定见 [知识结构](references/knowledge-contract.md)。新会话先解析配置的根节点及当前目录，不硬编码知识空间 ID；远程权限取决于使用者自己的账号。

## 内部共享协作
产品部的知识库是内部专家共用的权威来源。默认直接访问配置中的同一入口，不为每位专家建副本，不反复询问已共享文档的访问许可。个人登录仍使用自己的账号；仅遇实际错误时处理。
冷启动只新建本地个人批次，不重置共享文章、知识索引和团队确认记录。写前读最新版本，避免覆盖另一位专家刚完成的修改。

## 区分成果
- 专业知识：运动、饮食、心态与恢复、通用基础下的完整专题文章。文章内保留可识别的知识单元。
- 产品行为建议：证据用法、问法、输入字段等，进入产品架构与规则的候选文档；不混入生理知识，不直接改生产规则。
- 案例与反例：明确构造演示，进入案例库，不当真实研究证据。
- 未决分歧：进入管理区的待确认修改与争议，保留各方条件和来源，不伪造共识。

## 先读再改
读目标文章及版本，检查候选是否已存在、是否与原段落冲突。修正旧结论就替换对应段落，不仅在末尾追加相反观点。
能融入现有文章就复用；新主题足以独立阅读再新建文章；新分类只有现有分类确实容纳不了时才建。维护章节链接、关联知识 ID、导航和索引，移动优先保留原节点与链接。
不因为结构化就把完整文章拆成一堆无上下文短句；每个可检索片段需保留适用条件、边界和来源。

## 阶段性确认
由入口主动建议阶段整理，专家愿意后展示 1–3 项主要变化、目标位置和未决点，完整差异可展开。
使用 candidate.schema.json 准备候选：明确 before/after、目标章节及基准版本、证据类型、专家来源、适用范围和未知。
专家明确确认这份修改稿即可写入，不需第二负责人审批。普通讨论、沉默、对案例的“方向可以”不自动授权所有候选。批量确认必须列明候选 ID/版本；之后修改的内容不沿用旧确认。
candidate-seal 仅记录已实际获得的确认语句及引用，不能用脚本生成的“批准”代替用户意见。candidate-check 先检查内容哈希与远端最新版本。版本变动重读并处理冲突，再让专家确认有变化的部分。
审批记录不是密码或访问凭据，也不证明科学正确；保留研究支持、专家经验、待核验的区别。

## 写入与核验
使用当前可用 lark-doc / lark-wiki；身份显式 --as user。正文保存原文快照和变更记录；不输出 token 凭据。
只写专家批准范围，目录整理按用户已授权范围执行。请求结果未知先回读和查变更 ID，不能盲目重试重复追加。
写后 fresh fetch，核对目标章节确实含新内容、旧冲突已处理、链接可读、目标分类正确，再标“已写入”。本地候选变成 adopted 不等于飞书成功。
不得用失败写入替换为一份同名新文档假装完成；失败候选保留待同步并说明实际状态。

## 交付
保留原始文章、来源和版本；生成 manifest.json、articles/*.md、knowledge-units.jsonl，以及排除/争议清单。
默认生产检索只选择知识类且已确认、有效、适用范围明确的单元；研究支持与专家经验是独立标签，不能合并成同一证据等级。
目录页、历史架构、案例、未决知识都单独标记。未按单元审阅的历史文章为 unreviewed，不擅自给整库盖章。
export-kb 从已取回的文章快照与知识单元导出；不绕过飞书账号权限，不自动将资料上传第三方。取回正文失败时明确 partial，禁止用 URL 列表冒充全文数据集。
输出不等于已部署 RAG；权限过滤、切片策略、向量库和线上效果由研发后续实现。
