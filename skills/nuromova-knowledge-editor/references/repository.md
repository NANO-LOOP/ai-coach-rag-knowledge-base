# 本地编辑与 GitHub 协作

1. 读取 git status、HEAD 和目标文件，记录版本/哈希。保留已有未提交改动，不 reset、clean 或强制覆盖。
2. 先按 [专家维护边界](../../../docs/expert-maintenance.md) 区分三类文档资产与 Skill 执行层；后者必须完成两阶段确认。以下直接草稿写入授权仅适用于普通文档资产。
3. 从专家意见和当前正文形成具体修改，定位对应单元。新增使用 templates 的相应模板；移动保留 ID；拆分合并说明旧 ID 的去向。修改路径时更新专题、问题包、文内链接和 knowledge/sources/migration-map.json 的路径，保留原始归档哈希。
4. 写入前重新核对目标文件；基线已变则读取新版本并合并，不能覆盖他人修改。已明确授权的本地草稿维护直接完成；专业审阅与结构授权分开。
5. 更新 version、updated_at 和审阅状态；有实质改变的 confirmed 单元转 needs_review，新稿 draft。同步受影响的问题包引用和审阅记录。不得编造批准。
6. 运行 `python3 tools/catalog.py --write`、`python3 tools/catalog.py --check`、`git diff --check`，重读变更目标及引用。结构检查失败先修复，不标完成。需要模拟复验时明确哪些场景实际运行。
7. 查看完整差异，仅提交任务相关文件。按会话授权使用 Git 分支、提交、推送或 PR；未经授权不额外发消息。远程操作前确认 origin 与当前账号有权访问目标仓库，不切换到另一个连接账号。拉取采用不覆盖本地修改的方式，遇到分叉先检查和合并，禁止强推。
8. 输出文件链接、主要变化、校验结果、专家待审项，以及本地提交/远端推送状态。PR、提交成功或 confirmed 都不意味着已部署正式 RAG。
