# 模拟如何沉淀 Agent 逻辑

状态：验证设计，以下用例尚未执行。验证目标是可观察决策和状态变化，不要求生成完全相同的句子。

## 反馈归类

| 专家指出的问题 | 修改位置 | 示例 |
| --- | --- | --- |
| 专业结论、条件或证据有误 | knowledge/ 对应单元 | 某解释缺少适用条件 |
| 已有知识正确但 Agent 使用错误 | agent/ 架构、回合契约与对话原则 | 已知答案仍反复问；否定后仍沿用旧判断 |
| 通用输入字段、含义或阶段缺省有误 | agent/input-model.md 与 contracts 配套文件 | 无法区分缺失与明确否定 |
| 场景事实或时间线不合理 | 场景版本或构造案例 | 前后两次训练时间矛盾 |
| 角色、暂停或反馈接收错误 | 先核对现行规则的执行；确需改规则则走 Skill 两阶段确认 | 把专家点评记成运动者回答 |
| 存储、模型调用或检索执行失败 | 实际运行适配层待实现项 | 重试重复扣预算；读取文件失败 |

反馈路由与 Skill 修改确认统一遵循 [专家维护边界](../docs/expert-maintenance.md)。

一次反馈可关联多个类别，但分别记录证据和修改。结构性行为错误不能只改知识正文掩盖；个人偏好的话术也不能自动升级为普遍专业规则。

## 最小回归集

从 HYROX 问题包起步，保留固定输入、场景版本、知识快照与运行配置。

| 情境 | 预期可观察行为 |
| --- | --- |
| 前序训练未知 | 在有价值且预算允许时提问，不预认定加练 |
| 用户否定加练 | 撤回对应支持线索，考虑其他分支 |
| 用户记不清或拒答 | 保留未知，不写成没有训练或默认支持 |
| 已有明确训练记录 | 不重复询问同一事实 |
| 前后回答冲突 | 澄清冲突，保留来源与版本 |
| 确认练过但是否超计划未知 | 不把练过直接写成超计划或确定因果 |
| 专家突然点评 | 暂停模拟，反馈不污染运动者事实 |
| 仅纠正个人事实 | 更新事实并复查判断，保持模拟模式 |
| 预算耗尽或知识不足 | 有依据才给有限建议，否则标记不足 |
| 上游要求停止 | 停止普通训练建议，遵守配置的转交流程 |
| 重复事件或状态已过期 | 不重复更新或覆盖新状态；需实际适配层测试 |
| 来源被修订或读不到 | 标明版本差异或读取失败，不沿用伪造引用 |

## 每次修改的验证记录

在 review-data/<session-id>/agent-change.md 记录：反馈原话、归类、修改前行为、预期新行为、关联文件/版本、复现输入、反例、实际输出与结论。适合公开的去标识行为设计可整理到 agent/，构造案例写入 knowledge/cases/。

固定输入与其他配置，再比较修改前后。发生多项变更时记录混杂因素。专家点评、人工走读、当前会话模型试用、独立模型运行和 App 集成测试分别标记；未执行填 not_run。确认知识内容不等于 Agent 行为验证通过，Agent 行为符合预期也不等于训练效果有效。

## 维护边界走读场景

以下为待执行的行为验收，不因文件检查通过而标为通过：

| 专家反馈 | 应有处理 |
| --- | --- |
| “缺少一个输入字段” | 修订输入模型及 Schema/缺省/示例，保持 Skill 不变 |
| “已有答案就不应该再问” | 检查执行是否偏离现有 Agent 规则；需要修订时修改 Agent 文档 |
| “这个机制只适用于某类人” | 修改知识单元条件与版本，保留待审状态 |
| “让 Skill 遇到点评也继续扮演运动者” | 识别为角色执行规则变更；确认意图、展示具体差异，再确认后写入 |
| “整理进去”且意见同时含知识与 Skill 修改 | 完成已授权知识草稿；Skill 部分等待具体差异确认 |

## 场景生成验收

按 [生成约定](scenario-generation.md) 检查以下请求。以下是待运行任务，尚不代表实际生成质量通过；记录专家描述、追问、产物、结构检查与人工发现的问题。

| 输入请求 | 验收重点 |
| --- | --- |
| “业余羽毛球爱好者，刚打完球总感觉慢半拍” | 已明确运动后，不再重复问；睡眠、负荷等原因未知，不默认归因 |
| “我没想好，带我设计一个跑步案例” | 少量问题引导目标和可见数据，不要求填写整套技术字段 |
| “你选三个不同方向” | 提供主要未知或决策难点不同的场景，而非三个改名的 HYROX 加练案例 |
| “同一个场景，分别有训练记录、没记录和记录相互矛盾” | 保留共同基线，分别体现已知、缺失和冲突，不把没记录当作没训练 |
| “做一个状态正常、没必要再问的案例” | 允许正常结果，不为制造问题强加异常或无效追问 |
| “T0 跑步案例，顺便生成建议一周后的验证结果” | 说明该结果不属于 T0 可用输入；不擅自升级阶段，可保留独立的未来设计意图 |
| “做一个库里还没有的运动项目” | 定位可复用知识与专项缺口，允许探索性场景，不冒充已有专项知识 |
| “给我射击、骑行、羽毛球各一个，全部展开” | 尊重指定覆盖并生成三份结构化输入，不停在候选列表 |

## 本阶段完成标准

能从一条专家意见追溯到明确修改，并用一个支持场景和一个反例检查行为；能在回合记录中看出输入、知识、动作和状态之间的关系。此标准用于后续试用，不因设计文档写完而自动满足。
